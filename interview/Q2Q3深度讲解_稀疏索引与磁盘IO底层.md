# Q2/Q3 深度讲解：稀疏索引为什么快 —— 从磁盘 IO 底层讲起

> 上一篇讲了"列存为什么比行存快"（CPU 层面）。这一篇讲"稀疏索引为什么快"（磁盘 IO + 算法层面）。
> 读懂这篇，你就懂了 ClickHouse 和 MySQL 在**存储哲学上的根本分歧**。

---

## 第 0 章：先建立直觉——两种数据库服务两种查询

```
查询 A（点查）：SELECT * FROM users WHERE id = 12345;
  → 只需要 1 行，越快越好（OLTP / MySQL 的主场）

查询 B（分析）：SELECT city, SUM(amount) FROM orders WHERE dt > '2026-01-01' GROUP BY city;
  → 要扫几亿行做聚合（OLAP / ClickHouse 的主场）
```

**MySQL 用 B+Tree 服务查询 A，ClickHouse 用稀疏索引服务查询 B。**
两种索引没有谁更先进，而是**为完全不同的物理瓶颈设计**：
- B+Tree 的敌人是**磁盘随机 IO**（用树结构把随机读变成 3~4 次定位）
- 稀疏索引的敌人是**海量数据的扫描总量**（用排序+剪枝跳过无关数据块）

---

## 第 1 章：磁盘 IO 底层——一切设计的出发点

### 1.1 机械硬盘（HDD）：随机 IO 是灾难

```
HDD 读写一次数据的物理过程：
① 磁头臂摆动到目标磁道     —— 寻道时间 ~8 ms
② 盘片旋转到目标扇区       —— 旋转延迟 ~4 ms (7200转)
③ 读取数据                 —— 顺序读极快 (~200 MB/s)

随机读 4KB：≈ 12ms → IOPS ≈ 80~100 次/秒
顺序读 1GB：≈ 5 秒  → 吞吐 200 MB/s

⚠ 同样读 4KB，随机比顺序慢【几千倍】！
   （12ms 里 99.9% 的时间在"移动机械臂"，真正读数据不到 0.1ms）
```

### 1.2 固态硬盘（SSD/NVMe）：随机 IO 依然贵

SSD 没有机械臂，但仍不平等：

```
SSD 读写以【页】(4KB~16KB) 为单位，但擦除以【块】(数MB) 为单位
随机读 4KB：~100 µs → IOPS ≈ 数万（比 HDD 好 100 倍）
顺序读：     3~7 GB/s（NVMe）→ 仍比随机读 4KB 快百倍量级（按吞吐折算）

⚠ 结论不变：顺序访问永远碾压随机访问，只是差距从几千倍缩到百倍。
```

### 1.3 操作系统的对策：Page Cache（页缓存）

```
Linux 内核层：
磁盘 ──► page cache（页缓存，按 4KB 页缓存）──► 进程内存 ──► CPU 缓存

第一次读某页：慢（真磁盘 IO）
再次读同页：page cache 命中，内存速度（~100ns vs ~100µs，快 1000 倍）

关键：page cache 以【页】为单位缓存 → 访问模式越接近"顺序翻页"，命中率越高
```

> **记住这三条物理事实：**
> ① 随机 IO 比顺序 IO 慢 100~1000 倍（无论 HDD 还是 SSD）
> ② 数据块越大、越顺序，吞吐越高
> ③ page cache 按页缓存，顺序访问命中率高
> **B+Tree 和稀疏索引的所有设计，都是对这三条事实的回应。**

## 第 2 章：B+Tree 为什么长这样——为点查而生

### 2.1 朴素方案的问题

如果数据无序存放，找 `id=12345` 只能全表扫描 → 慢。
如果建一个"每行一个索引项"的有序数组，二分查找 log₂(1亿) ≈ 27 次 → 但数组插入要移动后面所有元素 → 写入灾难。

### 2.2 B+Tree 的解法：一棵为磁盘页定制的树

B+Tree 的每个节点 = **一个磁盘页**（InnoDB 默认 16KB）：

```
                    ┌─────────────────┐
                    │  根节点(1页)      │ [1, 100, 200, ...500]
                    └───┬────────┬────┘
              ┌─────────┘        └─────────┐
        ┌─────▼─────┐                  ┌───▼───────┐
        │ 中间节点    │ ...              │ 中间节点    │
        └──┬─────┬──┘                  └──────┬────┘
     ┌─────┘     └────┐              ┌───────┘
┌────▼────┐    ┌─────▼───┐      ┌────▼────┐
│ 叶子页:   │    │ 叶子页:  │ ...  │ 叶子页:  │   ← 叶子节点存数据/行指针
│[1..99]  │◄──►│[100..199]◄──►  │[...]    │   ← 叶子间双向链表（范围扫描用）
└─────────┘    └──────────┘      └─────────┘

树高计算（每页 16KB，每条索引项 ~16B → 每页 ~1000 个分叉）：
  1 层：1,000 行
  2 层：100 万行
  3 层：10 亿行      ← 10 亿行的表，树高只有 3~4！
```

### 2.3 点查 `id=12345` 的完整 IO 过程

```
根节点（常驻内存/page cache）    → 0 次磁盘 IO
第2层节点（大概率在 cache）      → 0~1 次
叶子节点                        → 1 次（cache miss 时）

→ 典型 3~4 次页读取，其中大部分命中缓存 → 点查 ~1ms 内
→ 这就是 MySQL 点查快的秘密：树很矮，随机 IO 次数被锁死在 3~4 次
```

### 2.4 但 B+Tree 的代价（分析查询的灾难）

```
查询：SELECT city, SUM(amount) FROM orders（扫全表 1 亿行）

B+Tree 的做法：沿叶子节点链表顺序扫描（B+Tree 其实也能顺序扫！）
但问题是：
① 行存：每读一行要把 100 列全部读出来（上一篇讲过，读 97 列垃圾）
② 每行 1KB → 1 亿行 = 100GB 数据从磁盘搬运
③ 无法 SIMD/向量化（数据不连续）
④ 缓存命中率低（有用的 amount 只占每个 cache line 的一小部分）

→ B+Tree 不是不能扫，而是【扫描的每一层都在浪费】：
   索引结构为点查优化（行定位），不为扫描吞吐优化
```

> **核心认知：B+Tree 把"随机 IO 次数"优化到极致（3~4 次），但扫描场景根本不在乎"定位一行要几次 IO"，在乎的是"总共要搬多少字节"。两种查询的物理瓶颈完全不同。**

## 第 3 章：ClickHouse 的反向思路——放弃点查，为扫描而生

### 3.1 哲学转变：不索引"每一行"，索引"每一块"

```
B+Tree：     1 亿行 → 1 亿个索引项 → 指数级定位单行
稀疏索引：    1 亿行 → 1.2 万个索引项（每 8192 行一个）→ 只定位"块"

"稀疏"（sparse）的含义：索引项密度低，不是每行都有，而是每 8192 行才一个。
```

### 3.2 为什么敢这么"粗"？——因为数据是排好序的

这是最容易被忽略的前提！**稀疏索引成立的前提是：part 内数据按排序键物理排好序。**

```
排序后的 UserID 列（每 8192 行切一个 granule）：

granule#0        granule#1        granule#2        ...
[1 .... 101]     [101 .... 205]   [205 .... 310]   ← 每块边界单调递增！
   ↑首行=101        ↑首行=205        ↑首行=310
   └─这就是 primary.idx 里的一条记录

因为有序：
  → 想找 UserID=300？只需二分"每块的首行值"就知道它在哪个块
  → 不需要每行的索引！块的边界就足够"圈出范围"
```

### 3.3 数学：稀疏索引为什么小到能全内存

```
8.87M 行表，index_granularity = 8192：
  granule 数 = 8,870,000 / 8192 ≈ 1,083 个
  primary.idx = 1,083 条记录 × ~90B ≈ 96.93 KB     ← 比一张图片还小！

10 亿行表：
  granule 数 ≈ 122,070 个
  primary.idx ≈ 11 MB                                ← 仍轻松全内存

对比 B+Tree：10 亿行 → 10 亿索引项 → GB 级，只能靠 page cache 分页缓存
```

**为什么"全内存"如此重要？** 二分搜索全程零磁盘 IO（对照第 1 章：省掉的是最贵的随机读）。

### 3.4 为什么是 8192 这个数？（权衡的艺术）

```
granule 太小（如 128 行）：
  ✗ 索引变大（1亿行 → 78 万条索引 → 内存压力）
  ✗ mark 文件变大
  ✓ 剪枝更精确，读的冗余行少

granule 太大（如 100 万行）：
  ✓ 索引极小
  ✗ 剪枝粗糙——找一个值要顺带扫 100 万行
  ✗ 无法充分利用 SIMD 批量过滤（一批处理量远小于 granule）

8192 = 2^13，是"索引内存开销"和"扫描冗余量"的平衡点：
  最坏多读 8192×2 = 16384 行冗余（官方文档明确的代价上界）
  但换来索引缩小 8192 倍
```

## 第 4 章：一次查询的完整字节流（mark → 压缩块 → SIMD）

这是 Q2/Q3 最核心的流程，逐字节拆解：

```
查询：SELECT URL FROM t WHERE UserID = 749927693

═════════════ 第①步：内存中二分 primary.idx ═════════════
   primary.idx（96KB，全在内存）：
   ┌─────────────────────────────┐
   │ mark#176: UserID=74990001   │ ← 目标 749927693 落在 [176,177) 区间
   │ mark#177: UserID=74998000   │
   └─────────────────────────────┘
   1,083 条 → 二分 ⌈log₂1083⌉ = 19 次比较 → 选中 granule #176
   ★ 磁盘 IO：0 次（索引在内存）★

═════════════ 第②步：查 mark 文件拿物理位置 ═════════════
   UserID.mrk2[176] = { block_offset: 42,   ← 在 .bin 里的第 42 个压缩块
                        granule_offset: 3,  ← 解压后块内第 3 个值起
                        rows: 8192 }        ← 这个 granule 有 8192 行
   ★ 磁盘 IO：mark 文件极小，大概率已在 page cache ★

═════════════ 第③步：读压缩块 + 解压 ═════════════
   UserID.bin 内部结构：
   ┌────────┬────────┬────────┬────────┐
   │压缩块0  │压缩块1  │ ...   │压缩块42 │ ← 每块 64KB~1MB（LZ4）
   └────────┴────────┴────────┰────────┘
                              ↑ seek 到 block 42（一次顺序定位）
   读出 block 42 → LZ4 解压（解压也是 SIMD 加速的）→ 得到明文列数据

═════════════ 第④步：流式读 8192 行 + SIMD 过滤 ═════════════
   解压后的 granule 是一个紧凑数组：
   [74990001, 74990001, ..., 749927693, ..., 74997999]
                              ↑
   SIMD 指令一条比较 16 个值，快速筛出 == 749927693 的行号
   → 产出 bitmap（哪几行命中）

═════════════ 第⑤步：晚物化——按 bitmap 读 URL 列 ═════════════
   URL.mrk2[176] → 定位 URL 列同一 granule → 解压 → 按 bitmap 取命中的 URL
   → 拼成结果行返回

总磁盘 IO：只读了 2 个列的各 1 个压缩块（而不是全表！）
总 CPU：19 次二分 + SIMD 扫 8192×2 行
→ 这就是"0.022s 全表扫 → 0.005s"的物理来源（官方实测数字）
```

> **和 B+Tree 对照**：B+Tree 点查 3~4 次页 IO 精确到行；稀疏索引 19 次内存比较 + 1~2 次压缩块 IO 精确到 8192 行。ClickHouse 用"精度换吞吐"，8192 行交给 SIMD 处理反而比多次磁盘定位更快。

## 第 5 章：mark 文件设计的三层精妙（面试高分点）

**为什么 primary.idx 不直接存物理位置，而要绕道 mark 文件？**

```
❌ 如果 primary.idx 里直接存物理偏移：
   → 索引条目变大（要存每列的 offset）
   → 索引可能超内存 → 违背"全内存"设计

✅ 分离设计（ClickHouse 的做法）：
   primary.idx：只存排序键值（小，全内存，负责"逻辑定位"到 granule#）
   列.mrk2：    存物理偏移（大，按需读，负责"物理定位"）

   精妙之处：
   ① 查询只用 2 列时，只需要读 2 个列的 mark 条目，不用碰其他 98 列的 mark
   ② 索引常驻内存的部分被压到最小
   ③ 每列独立 → 列存"按列读取"的特性得以贯穿到索引层
```

**自适应粒度下 .mrk2 和 .mrk 的区别：**
```
.mrk （固定粒度）：每条 2 个 8 字节（block_offset, granule_offset）
                    行数固定 8192，不用存
.mrk2（自适应粒度）：每条 3 个值（+ rows_count）
                    因为变长列（如长字符串）granule 行数 ∈ [1, 8192]，必须记录
```

## 第 6 章：二分搜索的 CPU 层面（加分细节）

`primary.idx` 是一个有序平坦数组，对它二分搜索在 CPU 层面近乎免费：

```
1,083 条 × ~90B ≈ 96KB：
  L1 = 32~64KB（可能放不下）
  L2 = 256KB+（轻松全放下）★

二分全程在 L2 缓存里完成，19 次比较 ≈ 19 × 几纳秒 ≈ 几十纳秒
对比一次磁盘随机 IO：~100µs = 100,000 ns

→ 索引搜索耗时是磁盘 IO 的【十万分之一】
→ 这就是为什么"索引必须全内存"是设计红线（落盘即性能崩塌）
```

ClickHouse 的二分还是 **branchless（无分支）实现**——用条件移动（cmov）代替 if 跳转，避免分支预测失败的流水线冲刷（呼应上一篇第 1.5 节）。

## 第 7 章：为什么排序连赢了三次（一次排序，三份收益）

排序键的作用远不止索引，这是 Q3 的深层答案：

```
           数据按 ORDER BY 排好序
                    │
     ┌──────────────┼──────────────────┐
     ▼              ▼                  ▼
 收益①剪枝       收益②压缩           收益③局部有序聚合
 稀疏索引成立     相同值挨在一起        GROUP BY 列若与排序键前缀
 （每块边界单调，  → run-length 编码     一致，可直接"顺序扫过"
  二分即可圈块）   → Delta 编码生效      免建哈希表（内存友好）
                  → 压缩率提升数倍      

例子（city 列排序后）：
[北京,北京,北京,...,北京, 上海,上海,...,上海, 广州,...]
 → run-length: (北京×8000, 上海×5000, 广州×3000) 几个数字代替几万个字符串！
 → 这也解释了为什么"低基数列放排序键前面"：让重复值物理相邻
```

## 第 8 章：Generic Exclusion Search——第二列失效的数学（Q3 核心）

### 8.1 问题：第二列为什么不能直接二分？

排序键 `(UserID, URL)` 是**字典序**：先按 UserID 排，UserID 相同才按 URL 排。

```
情况A：前置列 UserID 基数低（如只有 100 个用户）
granule#0   [u1: url a~z 排好]   ← 块内 URL 有序！
granule#1   [u1: url 继续有序]
granule#2   [u2: url a~z 排好]
→ 同一个 UserID 跨多个 granule → 这些块内部 URL 单调
→ 查 URL='x' 时：先二分定位 UserID 的块范围，再在块内对 URL 排除
→ ✅ 高效

情况B：前置列 UserID 基数高（如每行 UserID 都不同）
granule#0   [u1,u2,...,u8192 各不同]
granule#1   [u8193,...,u16384 各不同]
→ 每个 granule 的 URL 范围都是 [a, z]（各种 URL 都有）
→ "URL 在这个块的可能范围内？" → 每块都答"可能"
→ 无法排除任何块
→ ❌ 退化为全表扫描（官方实测：1083 块被迫选 1076 块）
```

### 8.2 一图记住

```
字典序排序 (UserID, URL)：

低基数 UserID 在前：              高基数 UserID 在前：
┌────────────────────┐           ┌────────────────────┐
│ u1: [a,z] 单调      │           │ u1,u2,u3,...,u8192 │
│ u1: [a,z] 单调      │           │ u8193,...,u16384   │ ← URL 每块
│ u1: [a,z] 单调      │           │ ...                │   都是[a,z]
│ u2: [a,z] 单调      │           └────────────────────┘
└────────────────────┘           URL 标记不单调
块内 URL 单调 → 可二分/排除        → 无法排除 → 全表扫
```

**排序键设计铁律（Q3 答案的根因）**：
1. 第一列 = 过滤最频繁 + 基数适中（太低浪费、太高毁掉后面列）
2. 低基数在前、高基数在后（保护后续列的单调性）
3. 多维度查询冲突 → 用 Projection 建第二套排序

## 第 9 章：终极对比表（面试直接背）

| 维度 | InnoDB B+Tree | ClickHouse 稀疏索引 |
|---|---|---|
| 为谁设计 | 点查（OLTP） | 扫描聚合（OLAP） |
| 优化目标 | 随机 IO 次数（3~4 次） | 总扫描字节量（跳过无关块） |
| 索引粒度 | 每行 1 条 | 每 8192 行 1 条 |
| 10 亿行索引大小 | GB 级（靠 page cache） | ~11MB（全内存） |
| 定位精度 | 精确到行 | 精确到 granule（+SIMD 补刀） |
| 前提条件 | 无（索引即排序结构） | **数据必须按排序键物理有序** |
| 写入代价 | 插入可能页分裂、重平衡 | 追加新 part，内存排序 |
| 范围扫描 | 叶子链表，但行存读放大 | 剪枝 + 列存 + SIMD，极致吞吐 |
| 点查 QPS | 数万/核 | 数百~数千/核 |
| 本质 | 用树高换 IO 次数 | 用"放弃行精度"换扫描吞吐 |

## 第 10 章：追问满分回答

**追问 1：稀疏索引最坏会多读多少数据？**
> 单个数据块最多多读 `index_granularity × 2 = 16384` 行（目标值恰在 granule 边界附近时，前后两块的边界行都要看）。这是官方文档写明的上界。代价换收益：索引缩小 8192 倍。

**追问 2：如果 WHERE 条件完全没命中排序键怎么办？**
> 稀疏索引失效（无法剪枝），退化为全 part 扫描。补救手段：①跳过索引（minmax/set/bloom）做二次剪枝；②Projection 建另一套排序；③把高频过滤列调整进排序键。

**追问 3：index_granularity 能调吗？什么时候调？**
> 能（建表 SETTINGS）。点查/高选择性查询多的场景可调小（如 4096）换取更精确剪枝；纯大扫描场景可调大减少索引内存。默认 8192 是通用平衡点，没有充分压测不要动。

**追问 4：primary.idx 超过内存会怎样？**
> ClickHouse 直接报错，不降级到磁盘——因为设计前提就是全内存二分，落盘后每次查询都变成随机 IO，性能断崖。这从侧面说明：排序键列不宜过多过长（索引条目 = 排序键值的元组）。

**追问 5：为什么 MySQL 不用稀疏索引？**
> 两个原因：①MySQL 无"part 内强制物理排序"机制，稀疏索引的前提不成立；②MySQL 的负载是点查+事务，需要行级精确索引。稀疏索引服务的是扫描场景——两者是负载决定架构，不是技术优劣。

## 一句话记忆锚点

> **B+Tree 用 3~4 次随机 IO 换"精确到行"；稀疏索引用"数据排序"换"索引缩小 8192 倍、全内存二分 19 次、只读命中的压缩块"。前者优化 IO 次数，后者优化扫描总量——点查选 B+Tree，扫描选稀疏索引。**
>
> **而这一切的地基是一句话：数据有序，块的边界就能代表块的内容。**
