# ClickHouse 模拟面试复盘 —— 生产实战 5 题（考点 + 解题思路 + 满分回答）

> 本文复盘一轮真实模拟面试的 5 道生产题。每题结构：**考点是什么 → 解题思路（怎么想）→ 满分回答（可直接背）→ 面试官追问预案**。
> 适用于：生产运维岗、大数据开发岗、DBA 岗的 ClickHouse 技术面。

---

## 第 1 题：每秒 1000 次单条 INSERT，跑了半小时会怎样？

### 考点是什么
① part 的生命周期理解；② ClickHouse 的 LSM 写入模型；③ 生产摄入最佳实践。**核心考察你懂不懂"CH 为什么必须批量写"。**

### 解题思路（怎么想）
从"一次 INSERT 在引擎里发生什么"出发 → 推出 part 产生速度 vs 合并速度的赛跑 → 得出结论。

### 满分回答

**报什么错**：`Too many parts`（写入直接被拒绝）。

**为什么会这样**（分三层讲）：
1. **机制**：ClickHouse 每次INSERT 都会生成一个不可变的 data part（数据片段）。该脚本 1000 次/秒 × 1800 秒 = **产生约 180 万个 part**。
2. **后台合并跟不上**：后台 merge 线程池把小 part 合并成大 part（k-way 归并），但合并速度有限（受 `background_pool_size`、磁盘 IO 限制）。产生速度 1000/s 远超合并速度 → active part 数单调上涨。
3. **保护机制触发**：当单分区 active part 数超过 `parts_to_throw_insert`（默认 3000）时，ClickHouse **主动拒绝写入保护自己**——否则 part 数失控会拖垮整个节点。

**后果不只是写入报错**：
- 查询变慢（查询规划要枚举所有 part，每个 part 都要开文件、读索引）；
- 内存上涨（每个 part 的元数据、主索引都要占内存）；
- 进入"死亡螺旋"：merge 占满 IO → 写入堆积 → part 更多 → merge 更慢。

**给业务方的建议**（按优先级）：
1. **攒批写入**：每批 ≥ 1 万行，每秒不超过 1~2 次 INSERT（官方推荐节奏）；
2. 前面加 **Kafka 缓冲**，消费者批量拉取批量写（生产标准做法）；
3. 如果客户端改不了，开启 **Async Insert**（`async_insert=1`，服务端自动攒批）；
4. 临时场景可用 Buffer 引擎，但要告知数据在内存有丢失风险。

### 面试官追问预案
- **"为什么 CH 不像 MySQL 一样支持频繁小写入？"** → 列存 + 不可变 part + 压缩块的设计，天生为批量优化；频繁小写产生海量小文件和元数据，违背 LSM 设计初衷。
- **"Too many parts 出现了怎么紧急恢复？"** → 停掉写入源头 → 等 merge 消化（可临时调大 `background_pool_size`）→ 必要时删掉部分小 part（有损）→ 根治靠攒批。
- **"part 和 partition 什么区别？"** → part 是**每次写入产生的数据片段**（物理目录）；partition 是**逻辑分区**（按分区键划分，如按月），一个分区内包含多个 part，**不同分区的 part 永不合并**。（⚠ 这是本题最容易暴露的概念混淆点）

## 第 2 题：副本 absolute_delay 持续增长，说明什么？

### 考点是什么
① ReplicatedMergeTree 复制机制的理解；② 生产运维排障能力；③ system 表的熟练度。**考察你有没有真正运维过复制集群。**

### 解题思路（怎么想）
absolute_delay = 副本落后于最新数据的时间。它涨说明**副本回放复制日志的速度 < 日志产生速度**。沿着复制链路逐环节找瓶颈：日志通知（Keeper）→ 数据传输（网络）→ 本地落盘（磁盘/CPU）→ 任务队列（堆积）。

### 满分回答

**这说明**：副本 B 消费复制日志的速度跟不上写入速度，数据持续落后（最终一致的"一致"被拉长），读打到 B 上会读到越来越旧的数据。

**至少 3 个根因 + 处理**：

| # | 根因 | 排查方法 | 处理 |
|---|---|---|---|
| 1 | **网络带宽打满**：副本间 fetch part 传输慢 | 监控副本间网络流量、`system.replicas` 的 fetch 队列 | 扩带宽 / 限流其他流量 / 错峰大批量迁移 |
| 2 | **副本机器资源不足**：CPU/IO 跑满，回放任务排队 | `system.replicas.queue_size`（队列堆积）、机器 CPU/IO 指标 | 扩容、把该副本上的其他负载迁走 |
| 3 | **大量重量级 mutation / 大 part 合并**拖慢回放 | `system.mutations`（未完成数）、`system.merges` | 控制 mutation（用删分区代替）、错峰执行 |
| 4 | **Keeper 抖动**：watch 通知延迟、日志读取慢 | Keeper 监控（延迟、znode 数）、`system.zookeeper` | 检查 Keeper 集群健康、znode 是否过多 |
| 5 | **副本宕机后恢复追赶**：正在全量对账补数据 | `system.replicas` 状态、logs_pointer 落后量 | 等待追赶完成，大表可预期较久 |

**兜底措施**：读流量用 `load_balancing` 策略避开高延迟副本；关键业务临时只读主副本。

### 面试官追问预案
- **"absolute_delay 具体怎么算的？"** → 副本记录的最近数据处理时间与当前时间的差值，本质是"最老未处理任务"的年龄。
- **"副本延迟会导致查询结果不一致吗？"** → 会，这是最终一致的体现：不同副本可能返回不同结果。规避靠避开延迟副本 / quorum 写 + sequential 一致性读。
- **"怎么监控告警？"** → `system.replicas` 的 `absolute_delay`、`queue_size` 配置阈值告警（如 delay > 60s 告警）。

## 第 3 题：查询从 200ms 突变 30 秒，排查顺序？

### 考点是什么
① 系统化排障方法论（不是背参数，是**有序的排查框架**）；② system 表全家桶；③ 剪枝失效的常见原因。**这是生产岗必考题，答得有无条理差距极大。**

### 解题思路（怎么想）
口诀："**先看查询日志定位病灶 → 再分两大方向：读多了 or 被拖慢了 → 最后看环境和数据变化**"。
- read_rows 暴涨 = 剪枝失效（数据层问题）
- read_rows 没变但变慢 = 资源争抢/溢写/并发（环境层问题）

### 满分回答（排查顺序）

**第 1 步：`system.query_log` 对比病灶**
```sql
SELECT event_time, query_duration_ms, read_rows, read_bytes,
       memory_usage, exception
FROM system.query_log
WHERE query LIKE '%该查询%' AND type = 'QueryFinish'
ORDER BY event_time DESC LIMIT 20;
```
对比正常 vs 异常时段的 `read_rows / read_bytes / memory_usage`，**把问题二分**：

**第 2 步（若 read_rows 暴涨 → 剪枝失效）**
- WHERE 条件是否命中**排序键前列**？（没命中 = 全 part 扫描）
- 是否**函数包裹列**破坏单调性？典型：`WHERE toDate(dt) = '2026-01-01'` 应改写为 `WHERE dt >= '2026-01-01' AND dt < '2026-01-02'`
- 类型是否不匹配（String 传数字等）导致索引失效
- 分区剪枝是否失效（查询没带分区键条件）

**第 3 步：`system.parts` 看 part 数**
```sql
SELECT count() FROM system.parts
WHERE table = 'xxx' AND active;
```
part 暴涨（如出现大量小写入/merge 跟不上）→ planning 开销剧增。

**第 4 步：`system.merges` + `system.mutations`**
是否有重量级后台任务（大 mutation、大 merge）抢 IO/CPU。

**第 5 步：`system.processes` + 资源层**
- 当前并发查询数、是否有大查询争抢 CPU
- 内存是否触顶、是否触发外部聚合溢写磁盘（ProfileEvents 里 spill 计数）

**第 6 步：数据本身的变化**
- 数据量是否突增（分区翻倍）
- GROUP BY 基数是否爆炸（分组数突增 → 哈希表暴涨）

**第 7 步：`EXPLAIN` 验证**
```sql
EXPLAIN indexes = 1 SELECT ...;
```
看索引使用情况和 granule 剪枝数量，验证前面的推断。

### 面试官追问预案
- **"最常见的根因是什么？"** → 经验上最常见：①查询条件没走排序键前列；②函数包裹破坏剪枝；③突发的并发大查询争抢。
- **"如果 read_rows 正常但 duration 高呢？"** → 转向资源争抢方向：并发、锁、IO 争抢、溢写磁盘、网络（分布式查询）。

## 第 4 题：ReplacingMergeTree 查出两条同订单记录（陷阱题）

### 考点是什么
① 对"**合并是异步的、最终生效的**"这一本质的理解；② 解决方案的权衡能力。**这是 ReplacingMergeTree 最高频的翻车点。**

### 解题思路（怎么想）
先想 ReplacingMergeTree 的去重**发生在什么时机**——是后台 merge 时，不是写入时也不是查询时 → 查询时数据可能还没被合并 → 重复是"正常现象"而不是 bug。

### 满分回答

**为什么会出现**：
ReplacingMergeTree 的去重发生在**后台 merge 阶段**（且只有当重复行被合并进**同一个 part** 时才会去重）。它是**异步、最终生效**的——查询执行的瞬间，可能：
1. 去重合并还没发生（刚写入不久）；
2. 重复行还在**不同的 part** 里（跨 part 的重复在查询时永远可见）。
所以"查到两条、状态还是旧的"是**设计内的行为**，不是数据损坏。

**至少 2 种解决方案 + 代价**：

| 方案 | 做法 | 代价 |
|---|---|---|
| **① 查询加 FINAL** | `SELECT ... FROM t FINAL WHERE ...` | 写法最简单，但 FINAL 强制在查询时应用合并逻辑，**性能差**（无法充分并行、CPU/内存开销大），大表多 part 时可能慢几十倍 |
| **② argMax 聚合** | `SELECT order_id, argMax(status, version) FROM t GROUP BY order_id` | 性能比 FINAL 好得多，但**所有查询 SQL 都要改写**，维护成本高 |
| **③ 定期 OPTIMIZE FINAL** | `OPTIMIZE TABLE t PARTITION xxx FINAL` | 一次性补救，I/O 极重、产生超大 part，**治标不治本**（新数据进来又重复） |
| **④ 换引擎/改架构** | VersionedCollapsingMergeTree，或写入端用 upsert 语义（删旧插新） | 写入逻辑复杂化，需要业务配合 |

**生产推荐组合**：常规查询用 **argMax**（性能好），低频对账场景才用 FINAL，同时监控 part 数让合并保持健康。

### 面试官追问预案
- **"为什么 CH 不设计成写入时就去重？"** → 列存 + 不可变 part，写入时去重需要查找已有数据（随机读+可能改已有 part），会毁掉批量写入的高吞吐。用"异步合并换写入吞吐"。
- **"跨 part 的重复什么时候能去掉？"** → 只有当这些 part 被合并到**同一个 part** 时。分区内 part 不断合并最终会收敛，但没有时间保证。
- **"FINAL 和 argMax 性能差多少？"** → 取决于 part 数和数据量，FINAL 在多 part 大表上常有数量级差距；argMax 只多一层聚合。

## 第 5 题：老板要把 MySQL 订单库迁到 ClickHouse（压力题）

### 考点是什么
① OLTP/OLAP 的边界意识；② **顶住业务压力给出正确技术判断的沟通能力**；③ 是否知道两库协同的标准架构。**这题答不好会显得"只会技术不懂选型"。**

### 解题思路（怎么想）
先肯定 CH 的价值（不贬低），再从订单业务的核心操作逐项对照 CH 的能力边界：**事务 → 点查 → 更新删除**，最后给出"不是替代而是协同"的架构。

### 满分回答

**先定调**：ClickHouse 确实快，但快的是**分析场景**。订单库的核心负载是交易（OLTP），两者设计哲学根本不同——直接迁移会用 CH 的短板去打 MySQL 的长板。

**三个角度**：

**① 事务角度**：
ClickHouse **没有 ACID 事务**——仅支持原子批量写入，无隔离级别、无多语句事务、无回滚。而订单业务的核心是"扣库存 + 创建订单 + 扣余额"这种**多表一致性事务**，CH 直接无法支撑。

**② 点查角度**：
CH 的稀疏索引最细只到 granule（8192 行），单条点查也要流式扫 8192 行做过滤，**单核 QPS 上限低**（几百~几千）。订单详情页、支付回调查单这种高频点查（数万 QPS）会直接把 CH 打爆。MySQL B+Tree 3~4 次 IO 精确到行，才是点查的正确工具。

**③ 更新/删除角度**：
订单状态频繁流转（待支付→已支付→已发货→完成）。CH 的 UPDATE/DELETE 是**重量级 Mutation**——重写整个 part、异步执行、不可回滚、与 merge 抢资源。高频状态更新会产生海量 mutation，**直接拖垮集群**。

**正确的用法（给老板的方案）**：
不是替代，而是**协同——交易库 + 分析库双库架构**：
```
业务读写 ──► MySQL（交易：事务、点查、状态更新）
                 │ binlog / CDC（Canal、Flink CDC）
                 ▼
             ClickHouse（分析：报表、审计、风控、用户行为）
```
MySQL 扛交易，变更通过 CDC 准实时同步到 CH 做分析。老板想要的"报表快、省成本"通过这个架构实现，且交易零风险。

### 面试官追问预案
- **"CH 一点事务能力都没有吗？"** → 有原子性（单批 INSERT 要么全成功要么全失败）和副本间幂等去重（块哈希），但没有隔离性和多语句事务。
- **"同步链路延迟多少？怎么做？"** → CDC 通常秒级延迟；用 Canal/Debezium/Flink CDC 订阅 binlog，攒批写 CH。
- **"CH 上确实要更新的场景怎么办？"** → ReplacingMergeTree（最终一致去重）/ CollapsingMergeTree（状态机型更新），查询层用 argMax 兜底——接受"最终一致"是使用 CH 的前提。
