# Q1 深度讲解：列存为什么比行存快？—— 从 CPU 硅片到 Linux 内核

> 这道题是 ClickHouse 的"地基"。向量化、SIMD、晚物化不懂，后面所有题都是空中楼阁。
> 本文从零讲起，配大量图，读完你会真正理解"快"是怎么来的。

---

## 第 0 章：先建立直觉——一次查询到底发生了什么

假设有一张订单表 `orders`，**1 亿行，100 列**。执行：

```sql
SELECT user_id, SUM(amount)
FROM orders
WHERE city = '北京'
GROUP BY user_id;
```

只用了 3 个列（`city` 过滤、`amount` 求和、`user_id` 分组），其余 97 列**根本不需要**。

**行存（如 MySQL InnoDB）的做法**：把整行（100 列）从磁盘读出来 → 组装成完整行 → 检查 city → 符合的留下。
→ 读了 100 列，97 列白读。

**列存（ClickHouse）的做法**：只读 `city` 列 → 算出哪些行是北京 → 只读这些行的 `amount` 和 `user_id`。
→ 只读了 3 列。

但"少读列"只是冰山一角。**真正的差距在 CPU 内部**。下面层层拆解。

## 第 1 章：CPU 微架构基础（不懂这个，后面全看不懂）

### 1.1 CPU 和内存的速度差有多大？

```
CPU 执行一条指令：~0.3 纳秒（3×10⁻¹⁰ 秒，光走 9 厘米的时间）
从内存读一个数据：~100 纳秒（CPU 在这期间能空转 300 条指令！）

打个比方：
CPU 速度  = 飞机（北京到上海 2 小时）
内存速度 = 走路（同样距离要走几个月）
```

如果 CPU 每算一个数都要等内存，那 CPU 99% 的时间在"干等"。所以 CPU 设计师发明了**缓存**。

### 1.2 缓存层次（Cache Hierarchy）

CPU 里内置了几层"小而快"的缓存，越靠近 CPU 越快越小：

```
┌─────────────────────────────────────────────────────────────┐
│                        CPU 核 (Core)                         │
│  ┌─────────────────────────────────────────────────────┐   │
│  │  寄存器 Registers（最快，纳秒级，几十个）             │   │
│  │    ↓ 数据从这里参与运算                               │   │
│  │  L1 缓存  ~1 纳秒   32~64 KB  （每核独享）           │   │
│  │    ↓                                                  │   │
│  │  L2 缓存  ~3~10 纳秒  256 KB~1MB（每核独享）         │   │
│  └─────────────────────────────────────────────────────┘   │
│  ┌─────────────────────────────────────────────────────┐   │
│  │  L3 缓存  ~30~50 纳秒  几 MB~几十 MB（所有核共享）    │   │
│  └─────────────────────────────────────────────────────┘   │
└──────────────────────────┬──────────────────────────────────┘
                           │ （最后才去内存）
                   ┌───────▼────────┐
                   │  内存 DRAM      │  ~100 纳秒  几 GB~几百 GB
                   │  （所有核共享）  │
                   └────────────────┘
```

**核心规则**：CPU 要用数据时，先查 L1 → L2 → L3 → 内存。在缓存里找到叫**命中（hit）**，找不到叫**未命中（miss）**，未命中就要去下一层取，代价指数级上升。

> 一次 L3 miss 去内存取数据，CPU 要干等 ~100 纳秒 = 浪费 ~300 条指令的算力。**缓存命中率就是数据库性能的命根子。**

### 1.3 缓存行（Cache Line）—— 最小的搬运单位

CPU **不是按字节、也不是按行**搬数据，而是按 **cache line（缓存行）**，固定 **64 字节**。

```
内存里的数据                    CPU 搬运时
┌──┬──┬──┬──┬──┬──┬──┬──┐    ┌───────────────────────────┐
│a │b │c │d │e │f │g │h │ →  │ 一整个 64 字节 cache line  │ → 整块塞进 L1
└──┴──┴──┴──┴──┴──┴──┴──┘    └───────────────────────────┘
```

**关键含义**：即使你只要 1 个字节，CPU 也会把它周围的 64 字节**一起搬进缓存**。
- 如果接下来访问的数据在这 64 字节里 → **命中，超快**（这叫**空间局部性**）。
- 如果不在 → miss，再去内存搬。

**所以：数据排得越紧凑、越连续，缓存命中率越高。** 这是列存快的物理根源！

### 1.4 硬件预取器（Prefetcher）—— CPU 会"预测"你要读什么

CPU 里有个硬件单元叫**预取器**。它观察你的访问模式：
- 如果你**连续顺序**读内存（地址 a, a+64, a+128, a+192...），预取器会发现这个规律，**提前**把后面的数据搬进缓存。
- 如果你**随机跳跃**读（地址 a, 然后 x, 然后 q...），预取器猜不到，每次都是 miss。

```
顺序访问（列存典型）：        随机访问（行存典型）：
读 addr 0   → 命中             读 addr 0   → 命中
读 addr 64  → 预取器已提前搬好  读 addr 9999 → miss！（预取器没猜到）
读 addr 128 → 预取器已提前搬好  读 addr 333  → miss！
读 addr 192 → 命中（流水般顺畅）读 addr 77777→ miss！
✅ 流水线全速运转               ❌ CPU 一直在干等内存
```

> 记住：**顺序访问是 CPU 的"顺风车"，随机访问是"逆风"。** 列存天然顺序，行存天然随机。

### 1.5 指令流水线（Pipeline）与分支预测（Branch Prediction）

CPU 执行指令不是一条一条来，而是像**工厂流水线**：取指 → 译码 → 执行 → 访存 → 写回，多条指令重叠进行。

但遇到 `if/else`（分支）就麻烦了：流水线不知道下一步走哪条路，必须等条件算出来。为了不干等，CPU 会**猜**（分支预测）：
- 猜对 → 流水线继续，无损耗。
- 猜错 → **冲刷流水线（pipeline flush）**，已经做的功全废，重来，代价 ~15~20 个时钟周期。

```
if (条件) {         分支预测器先猜"条件成立"，提前执行 if 块
   执行 A             ↓
} else {          如果猜错（实际走 else）：
   执行 B          ──► 冲刷！A 的计算全废，重新执行 B  ◄── 浪费 15~20 周期
}
```

**虚函数调用**就是分支预测的噩梦（后面讲向量化时细说）。

## 第 1 章 小结（先记住这 4 条物理事实）

```
①  CPU 比内存快 300 倍，缓存命中率决定性能。
②  CPU 按 64 字节 cache line 搬数据 → 数据越紧凑越连续越占便宜。
③  顺序访问触发硬件预取，随机访问全是 miss。
④  分支预测猜错要冲刷流水线，代价很大。

行存违反了全部 4 条；列存天然符合全部 4 条。这就是"快"的物理根源。
```

## 第 2 章：行存的 CPU 痛点（反面教材）

还是那张表：1 亿行 × 100 列。行存在磁盘上的样子：

```
行存布局（每行所有列挨在一起）：
┌────────────────────────────────────────────────────────┐
│ 行1: [id=1, name=张三, city=北京, amount=100, ...(还有96列)] │
│ 行2: [id=2, name=李四, city=上海, amount=200, ...(还有96列)] │
│ 行3: [id=3, name=王五, city=北京, amount=150, ...(还有96列)] │
│ ...                                                      │
└────────────────────────────────────────────────────────┘
```

要算 `WHERE city='北京'` 的 SUM(amount)，行存做了什么？

```
读行1 → 整行 64 字节 cache line 里混着 id/name/city/amount/...96列
        → 取出 city 判断 = '北京' ✓
        → 取出 amount 累加
        ⚠ 但这一行的 id/name/96列全被读进缓存了，白占地方，还挤掉了别的有用数据

读行2 → 又是整行混在一起，city='上海' ✗ 跳过
        ⚠ amount 白读了吗？其实根本没读 amount，但整行已进缓存，浪费

问题1【CPU 缓存浪费】：每个 cache line 64 字节里，可能只有 amount(8字节)
        是有用的，其余 56 字节是 id/name/...96列的垃圾数据。命中率 < 10%。
问题2【带宽浪费】：为了累加 amount，被迫把 100 列全读进 CPU，内存带宽浪费 100 倍。
问题3【无法 SIMD】：amount 不连续，散在各行里，CPU 没法"一条指令加 16 个 amount"。
问题4【指针追逐】：行存常靠行指针跳转，每次跳转一个 cache miss。
```

**一句话：行存查聚合，CPU 大部分时间在干等内存搬垃圾数据。**

## 第 3 章：列存的 CPU 优势（正面教材）

同样的表，列存布局（每列单独连续存储）：

```
列存布局（每列单独成块，紧凑排列）：
city 列：   [北京, 上海, 北京, 广州, 北京, ...]   ← 连续紧凑
amount 列： [100,   200,  150,   80,    300,  ...]  ← 连续紧凑
id 列：     [1,     2,    3,     4,     5,    ...]
```

查 `WHERE city='北京' 的 SUM(amount)`：

```
第1步：只扫 city 列（连续紧凑）
       一个 cache line 64 字节，能装下好几个 city 值（字符串字典编码后甚至更多）
       → 命中率高，预取器提前搬后续数据，顺序流般顺畅
       → 算出哪些行是"北京" → 行号列表 [0,2,4,...]

第2步：按行号，只读 amount 列里对应位置（也是连续紧凑）
       → 同样顺序访问、高命中、能 SIMD

⚠ 全程没碰 id/name/96列，零浪费！
```

**列存快的第一层原因就是：紧凑 + 连续 → 缓存命中 + 预取 + 少读无用数据。** 但这还不够，下面三把刀更狠。

## 第 4 章：向量化执行（Vectorized Execution）

这是 ClickHouse 快的**第二板斧**。要理解它，先看传统数据库怎么执行查询。

### 4.1 Volcano 迭代器模型（传统行式数据库的执行方式）

传统数据库（PostgreSQL、MySQL 早期、火山模型）每个算子有个 `next()` 方法，**每次返回一行**：

```
查询：SELECT SUM(amount) FROM t WHERE city='北京'

执行计划（自底向上调用）：
┌──────────────┐
│   Aggregate   │  ← 聚合算子
│  (SUM)        │
└──────┬───────┘
       │ 调用 child.next() 拿一行
┌──────▼───────┐
│    Filter    │  ← 过滤算子
│ city='北京'   │
└──────┬───────┘
       │ 调用 child.next() 拿一行
┌──────▼───────┐
│  TableScan   │  ← 扫表算子
└──────────────┘
```

**每产生一行，就发生一串调用**：
```
Aggregate.next() → 调 Filter.next()
                   Filter.next() → 调 Scan.next()
                                  Scan.next() → 返回行1
                   Filter 检查行1，符合 → 返回给 Aggregate
Aggregate 累加，再调 Filter.next() ... 循环
```

1 亿行 → **这种调用链发生 1 亿次**！

### 4.2 Volcano 模型的两大致命伤

**致命伤 1：虚函数调用开销**

这些 `next()` 都是**虚函数**（C++ 多态）。虚函数调用：
```
普通函数：直接跳到函数地址执行（1 条指令）
虚函数：  ① 先查对象的 vtable（虚函数表）指针
          ② 从 vtable 取出函数地址      ← 这是个间接跳转
          ③ 再跳过去执行
```

**间接跳转 = 分支预测器的噩梦**。每次跳转目标不同，预测器猜不准 → 流水线冲刷。1 亿次虚调用，每次浪费十几周期 → **几十亿周期的纯浪费**。

**致命伤 2：每行一次，无法 SIMD**

每次只处理一行，CPU 寄存器里只有 1 个值，根本用不上 SIMD（SIMD 要一批值，下一章讲）。流水线也无法填满。

### 4.3 向量化执行（ClickHouse 的解法）

向量化把"一次一行"改成"**一次一批（一个向量/块）**"。一批通常是 65536 行或一个 granule（8192 行）。

```
Volcano（每次一行）：          向量化（每次一批）：
Aggregate ◄─ 行 ◄ Filter       Aggregate ◄─[一批8192行]◄ Filter
Filter   ◄─ 行 ◄ Scan          Filter   ◄─[一批8192行]◄ Scan

1 亿行 = 1 亿次调用链           1 亿行 / 8192 ≈ 1.2 万次调用链
                                虚调用摊薄了 8192 倍！
```

**直观对比**：
```
Volcano:   next()→行  next()→行  next()→行 ... (1亿次)
           ▲虚调用   ▲虚调用    ▲虚调用
           每次都查 vtable、间接跳转、可能冲刷流水线

向量化:    next()→[8192行]  next()→[8192行] ... (1.2万次)
           ▲虚调用（8192行只付一次）
           然后这 8192 行在一个紧凑数组里 → 可以 SIMD 批量处理
```

### 4.4 为什么向量化能配 SIMD？

因为一批数据是**同类型、连续排列的数组**（比如一个 `amount[8192]` 的 double 数组）。这种数据正好是 SIMD 指令的"口粮"。Volcano 每次只有 1 个孤零零的值，SIMD 无用武之地。

> **向量化是 SIMD 的"运输车"，SIMD 是向量化的"发动机"。** 两者缺一不可，而列存的紧凑布局是它们的"公路"。

## 第 5 章：SIMD（Single Instruction Multiple Data）

这是 ClickHouse 快的**第三板斧**，也是最硬核的。我从 CPU 寄存器讲起。

### 5.1 普通（标量）指令 vs SIMD 指令

假设要把两个数组相加 `c[i] = a[i] + b[i]`，每个数组 16 个 float（每个 4 字节）。

**普通标量指令（一次算一个）**：
```
CPU 通用寄存器一次只装一个 float：

循环 16 次：
  load  r0, a[0]     ; 取 a[0]
  load  r1, b[0]     ; 取 b[0]
  add   r2, r0, r1   ; 相加
  store c[0], r2     ; 存 c[0]
  load  r0, a[1]     ; 取 a[1]   ... 重复 16 次
  ...

→ 大约 16 × 4 = 64 条指令
```

**SIMD 指令（一次算一批）**：

SIMD = Single Instruction Multiple Data（单指令多数据）。CPU 有专门的**向量寄存器**，特别宽，一次能装很多个值：

```
向量寄存器宽度：
  SSE   : 128 位 = 4 个 float（或 2 个 double）
  AVX2  : 256 位 = 8 个 float
  AVX-512: 512 位 = 16 个 float  ← ClickHouse 手写优化的目标

一条 AVX-512 加法指令，同时算 16 个 float：
┌─────────────────────────────────────────────────────────────┐
│  zmm0:  [a0,a1,a2,a3,a4,a5,a6,a7,a8,a9,a10,a11,a12,a13,a14,a15]  │  16个float
│  zmm1:  [b0,b1,b2,b3,b4,b5,b6,b7,b8,b9,b10,b11,b12,b13,b14,b15]  │  16个float
│         ↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓             │
│  一条 vaddps 指令：                                          │
│  zmm2 = zmm0 + zmm1  (同时算16组加法!)                       │
│         ↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓             │
│  zmm2:  [c0,c1,c2,...,c15]  ← 16个结果一次产出                │
└─────────────────────────────────────────────────────────────┘
```

**伪汇编对比**：
```
标量（16次循环）:                 AVX-512（1次）:
  loop:                            vmovups zmm0, [a]    ; 一次加载16个float
    vaddss xmm0, [a+idx], [b+idx] ; 加1个     vaddps  zmm0, zmm0, [b] ; 一条指令加16个
    vmovss [c+idx], xmm0          ; 存1个     vmovups [c], zmm0      ; 一次存16个
    add idx, 4                    ;
    cmp idx, 64                   ;
    jl loop                       ;
  ~ 64+ 条指令 + 分支               3 条指令！无分支！
```

**16 个 float 的加法，从 ~64 条指令降到 3 条指令。** 这就是 SIMD 的威力。

### 5.2 SIMD 能加速哪些操作？

不只是加法。聚合里常见的操作几乎都有 SIMD 指令：
- 比较（`==`, `<`）→ 一次比 16 个，生成 bitmap
- 加减乘除
- min/max（一次找 16 个里的极值）
- 位运算（AND/OR，用于 bitmap 交集）
- 聚合（sum 用 SIMD 横向累加）

所以 `SUM(amount)`、`COUNT`、`WHERE` 过滤在列存 + 向量化 + SIMD 下，速度是行存的几十倍。

### 5.3 SIMD 的前提条件（为什么行存用不上）

SIMD 要求数据**同类型 + 连续排列**（一个数组）。
- **列存**：`amount` 列就是一个连续的 double 数组 → 完美适配 SIMD。
- **行存**：`amount` 散落在各行的不同位置 → 没法一次加载 16 个连续 amount → SIMD 失效。

> **这就是为什么"列存 + 向量化 + SIMD"是三位一体的：列存提供连续数据，向量化批量运输，SIMD 批量计算。行存一个都用不上。**

### 5.4 ClickHouse 的"挑内核"黑科技

同一段向量化代码，ClickHouse 用编译器生成**多个版本**：
```
版本1：标量版（兼容老 CPU，最低 SSE4.2）
版本2：AVX2 自动向量化版
版本3：AVX-512 手写汇编优化版（最快）
```
程序启动时检测 CPU 支持哪些指令集，**运行时选最快的版本**。所以 ClickHouse 在 15 年前的老服务器到最新的服务器都能跑，且总是用上最快的指令。

## 第 6 章：晚物化（Late Materialization）—— 你最需要搞懂的概念

### 6.1 什么是"物化"（Materialization）

**物化 = 把数据"组装"成最终结果行**。

查询 `SELECT user_id, amount FROM t WHERE city='北京'`，最终要返回的是**行**（user_id + amount 拼一起）。把列拼成行这个过程，就叫物化。

### 6.2 早物化（行存的做法）—— 浪费之王

```
表 100 列，查询只用了 3 列（city 过滤, user_id, amount），1 亿行，北京 100 万行

早物化流程（边读边组装完整行）：
┌──────────────────────────────────────────────────────────┐
│ 扫表 → 读第1行【全部100列】→ 组装成完整行(100列)            │
│        → 检查 city='北京'? ✗ → 丢弃整行                    │
│ 读第2行【全部100列】→ 组装 → city='上海' ✗ → 丢弃           │
│ 读第3行【全部100列】→ 组装 → city='北京' ✓ → 取 user_id,amount│
│ ... 重复 1 亿次                                            │
│                                                            │
│ 后果：                                                     │
│  • 读了 1亿 × 100列 = 100亿个列值（实际只需3列）            │
│  • 组装了 1亿次完整行（99%被丢弃，组装白费）                │
│  • 内存/CPU/带宽全部浪费在 97 个无关列上                    │
└──────────────────────────────────────────────────────────┘
```

**早物化的问题：先花钱组装，后过滤。结果大部分组装工作白做了。**

### 6.3 晚物化（列存的做法）—— 精打细算

晚物化的核心思想：**先在过滤列上算出"哪些行命中"，最后才去读其他列组装。**

```
同样的查询，晚物化流程：

第1步【先只扫过滤列 city】
   city 列紧凑连续 → 高速扫完 1 亿个 city 值（SIMD 比较）
   → 产出 bitmap（位图）：标记哪些行是"北京"

   ┌─────────────────────────────────────────────┐
   │ 行号:    0   1   2   3   4   5   6 ...      │
   │ city:  北京 上海 北京 广州 北京 上海 北京 ...  │
   │ bitmap:  1   0   1   0   1   0   1  ...      │  ← 1=命中, 0=跳过
   └─────────────────────────────────────────────┘
   结果：1 亿行里只有 100 万行命中（bitmap 很稀疏）

第2步【按 bitmap，只读需要的列、只读命中的行】
   要 user_id 列 → 但只读 bitmap=1 的那 100 万个位置（不读 9900 万个）
   要 amount 列 → 同样只读命中的 100 万个

第3步【最后才组装成结果行】
   把 100 万个 (user_id, amount) 拼成结果行返回

┌──────────────────────────────────────────────────────────┐
│ 晚物化总开销：                                            │
│  • city 列：读 1 亿个（必须，要过滤）                      │
│  • user_id 列：只读 100 万个（命中部分）                   │
│  • amount 列：只读 100 万个                                │
│  • 只组装 100 万行结果（不组装 9900 万废行）               │
│  • 其余 97 列：完全不读！                                  │
└──────────────────────────────────────────────────────────┘
```

### 6.4 早物化 vs 晚物化 直观对比图

```
┌──────────── 早物化（行存，浪费）────────────┐
│  读 100列 ──► 组装整行 ──► 过滤 ──► 取2列    │
│  (全读)      (全组装)     (丢99%) (只留2列)  │
│  浪费：97列的读 + 9900万次无效组装            │
└──────────────────────────────────────────────┘

┌──────────── 晚物化（列存，精算）────────────┐
│  读 city列 ──► 算bitmap ──► 按bitmap读2列   │
│  (只读过滤列)  (哪些命中)   (只读命中行)      │
│  ──────────────────────────► 组装结果行       │
│  （最后才组装）                               │
│  省了：97列 + 9900万行的无效读和组装          │
└──────────────────────────────────────────────┘
```

### 6.5 晚物化的"代价"（面试追问重点）

晚物化不是免费的，它的代价是：

**代价 1：bitmap 要占内存、要反复读写**
bitmap 本身是个数组（1 亿 bit ≈ 12 MB）。算出来后要存在内存，后续读其他列时要反复查它。如果 bitmap 不在缓存里，每次查也是一次 miss。

**代价 2：当过滤选择性低（命中率高）时，晚物化反而更慢**
```
极端情况：WHERE city != '火星'  → 99.99% 的行都命中
bitmap 几乎全是 1 → 晚物化没省什么（该读的还得读）
反而多了一次 bitmap 计算和查 bitmap 的开销 → 比早物化还慢一点
```
所以晚物化在**高选择性（命中少）**时收益巨大，在**低选择性（命中多）**时收益小甚至轻微负优化。ClickHouse 会根据选择性动态决策。

**代价 3：随机读**
按 bitmap 读"命中的行"，行号可能不连续（比如第 0,2,4 行命中）。读 amount[0]、amount[2] 这种跳跃访问，比顺序读差。不过列存里这个跳跃通常在同一个小数组内，比行存的跨行跳转好得多。

> **记忆要点**：晚物化 = "先过滤再花钱组装"，省的是无关列的读取和无效组装。代价是 bitmap 开销，且对低选择性查询收益小。

## 第 7 章：压缩（Compression）—— 不只是省磁盘

这是 ClickHouse 快的**第四板斧**。

### 7.1 压缩为什么能加速（不只是省空间）

很多人以为压缩只是为了省磁盘，错！**压缩主要省的是 CPU 最头疼的内存带宽**。

```
数据从磁盘 → 内存 → L3 → L2 → L1 → 寄存器 → CPU 计算

如果数据压缩 10 倍：
  磁盘读 1/10 的字节
  内存传输 1/10 的字节     ← 内存带宽是稀缺资源！
  缓存里能装下 10 倍的数据  ← 命中率飙升
  最后在 CPU 里解压（解压用 SIMD，极快）→ 计算
```

**核弹级结论**：内存带宽往往是大数据查询的真正瓶颈（不是 CPU 算力）。压缩让通过内存的数据量减少 10 倍 → 等效于内存带宽扩容 10 倍 → 查询快 10 倍。而解压的 CPU 开销远小于省下的内存等待。

### 7.2 为什么列存压缩率远高于行存？

```
行存一行：[id=1, name="张三", city="北京", amount=100.0, ts=2026-01-01...]
类型混杂（整数、字符串、浮点、时间），相邻数据差异大，压缩算法找不到规律。

列存 city 列：["北京","北京","上海","北京","北京","北京","广州",...]
全是同类字符串，大量重复 → 字典编码（北京=1,上海=2,广州=3）→ 变成 [1,1,2,1,1,1,3]
再 LZ4 压缩 → 极致压缩率（10~50 倍）
```

ClickHouse 还针对不同列用专用编码：
- 时间戳列 → `Delta` 编码（存差值，相邻时间戳差值小且重复）
- 低基数字符串 → `LowCardinality`（字典编码）
- 时序浮点 → `Gorilla`（XOR 编码）

## 第 8 章：Linux 层面（面试加分项）

讲完 CPU，再讲 Linux 内核怎么配合，体现你的深度。

### 8.1 页缓存（Page Cache）

```
读数据流程（Linux）：
  磁盘数据 ──► 内核 page cache（页缓存）──► 用户态进程内存 ──► CPU 缓存

第一次读：磁盘 → page cache → 进程内存（慢）
第二次读：page cache 命中 → 进程内存（快，跳过磁盘）

ClickHouse 的 part 文件第一次查询时读进 page cache，
后续查询命中 page cache，速度飞快。所以"热数据"查询远快于"冷数据"。
```

**生产启示**：内存足够大让热数据常驻 page cache，是 CH 性能的关键。这就是为什么 CH 服务器要配大内存（不只是给聚合用）。

### 8.2 内存带宽瓶颈（Memory Bandwidth Wall）

现代 CPU 算力极强（多核 + SIMD），但内存带宽有限（DDR4 ~20~30 GB/s，DDR5 ~50~60 GB/s）。

```
一个 32 核 CPU，每核 AVX-512 能算 16×float/周期 × 3GHz = 算力惊人
但内存只能喂 ~50 GB/s 的数据
→ CPU 经常"饿着"等内存送数据

所以：压缩（减少内存数据量）和 缓存命中（不经过内存）才是真正的加速器。
```

ClickHouse 所有优化（列存、压缩、SIMD、晚物化）本质都在**减少要从内存搬的数据量**。

### 8.3 NUMA（多 CPU 架构）

多路服务器（2+ CPU）是 NUMA 架构：每个 CPU 有"本地内存"，访问别的 CPU 的"远端内存"要慢 1.5~2 倍。

```
┌─── NUMA Node 0 ───┐     ┌─── NUMA Node 1 ───┐
│ CPU 0  本地内存 0   │◄───►│ CPU 1  本地内存 1   │
│ (快)               │ 互联 │ (快)               │
└────────────────────┘     └────────────────────┘
        │                          │
        └──访问 Node1 内存：慢 1.5~2x──┘

生产建议：CH 进程用 numactl 绑定到某个 NUMA node，避免跨 node 访存。
```

### 8.4 大页（Huge Pages）

Linux 默认内存页 4KB。TB 级数据 → 几亿个页表项 → TLB（地址转换缓存）miss 频繁 → 访存变慢。

启用 2MB 大页 → 页表项减少 512 倍 → TLB 命中率提升 → 大内存查询加速。CH 建议开 transparent hugepages 或显式大页。

### 8.5 CPU 亲和性（CPU Affinity）

把 CH 的查询线程绑定到固定核，避免操作系统把线程在核间迁移（迁移会导致 L1/L2 缓存全失效）。生产用 `taskset` 或 cgroups 绑核。

## 第 9 章：四板斧协同总结（面试时这么答）

列存为什么比行存快？**不是一招，是四板斧协同，且每一板斧都建立在上一板斧之上**：

```
┌─────────────────────────────────────────────────────────────┐
│ 第①板斧：列式存储（基础）                                    │
│   每列单独连续存储 → 紧凑、顺序访问                           │
│   → 缓存命中高 + 硬件预取生效 + 只读需要的列                  │
│   ↓ 为以下三招提供"原料"                                     │
├─────────────────────────────────────────────────────────────┤
│ 第②板斧：向量化执行（建立在列存上）                          │
│   一次处理一批（8192行）而非一行                              │
│   → 虚函数调用摊薄 8000 倍，流水线不 stall                   │
│   → 把连续数据"成批"喂给 SIMD                                │
├─────────────────────────────────────────────────────────────┤
│ 第③板斧：SIMD（建立在向量化上）                              │
│   一条 AVX-512 指令同时处理 16 个值                          │
│   → 算力提升 8~16 倍                                         │
│   → 但前提是数据连续（列存+向量化提供）                       │
├─────────────────────────────────────────────────────────────┤
│ 第④板斧：压缩 + 晚物化（建立在以上全部）                     │
│   高压缩比 → 内存带宽等效扩容 10 倍                          │
│   晚物化 → 只读命中行、不组装废行                            │
│   → 把宝贵的内存带宽用在刀刃上                               │
└─────────────────────────────────────────────────────────────┘

底层物理原理（贯穿四板斧）：
  • CPU 比内存快 300 倍 → 缓存命中率是命根子
  • 64 字节 cache line + 硬件预取 → 顺序连续访问是顺风车
  • 分支预测冲刷 → 虚函数和随机跳转是大敌
  • 内存带宽是真正瓶颈 → 减少数据搬运量是终极优化

行存违反了全部物理原理；列存 + 向量化 + SIMD + 压缩 + 晚物化 顺应了全部物理原理。
这就是 ClickHouse 比 MySQL 快 100~1000 倍的根本原因。
```

## 第 10 章：面试官追问与满分回答

**追问 1：晚物化的代价是什么？什么时候反而更慢？**
> 晚物化要维护 bitmap，占内存且反复查（可能 cache miss）。更关键的是，当**过滤选择性低（命中率高）**时——比如 `WHERE id > 0` 命中 99% 行——bitmap 几乎全 1，晚物化没省数据读取，反而多了一次 bitmap 计算开销，可能比早物化还略慢。ClickHouse 会根据谓词选择性动态选择策略。

**追问 2：向量化执行和代码生成（codegen）哪个好？**
> 各有优劣。向量化对短查询友好（无编译开销）、代码可维护、天然配 SIMD；codegen（如 Hyper）把算子链编译成一个函数、消除虚调用、数据留寄存器，对长查询和复杂表达式更优。ClickHouse 用**混合策略**：默认向量化，对重复出现的表达式做 LLVM codegen。二者不是对立而是互补。

**追问 3：既然压缩这么好，为什么不把每列压到极致（ZSTD level 22）？**
> 因为**解压要花 CPU**。ZSTD level 22 解压比 LZ4 慢几倍。热数据高频扫描的列，解压成为新瓶颈，应该用快的 LZ4；冷数据用高压缩 ZSTD 省存储和带宽。这就是冷热分层 + 分层压缩的原因。

**追问 4：SIMD 这么快，为什么行存不用 SIMD？**
> SIMD 要求"同类型数据连续排列"。行存里同一个列的值散在各行，地址不连续，没法一条指令加载 16 个。只有列存把同列数据紧凑排列，SIMD 才有用武之地。这是物理限制，不是行存不想用。

**追问 5：列存有什么缺点？（考察全面性）**
> ① 单行点查慢（要定位到列内偏移，最细到 granule 8192 行）；② 单行更新/删除难（列存压缩块，改一行要重写整块）；③ 不擅长事务（无 ACID）；④ 宽表整行插入要写多个列文件。所以列存适合 OLAP（大批量写、聚合分析），不适合 OLTP（点查、事务、高频小写）。

## 一句话记忆锚点

> **列存让数据"排得整齐"（缓存友好），向量化让数据"成批发货"（摊薄开销），SIMD 让 CPU"批量计算"（一条指令干 16 份活），压缩让内存"少搬垃圾"（省带宽），晚物化让 CPU"先筛后装"（不白组装）。四招环环相扣，全靠"数据连续"这一块地基。**
