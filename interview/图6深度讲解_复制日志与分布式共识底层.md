## 第 0 章：先建立直觉——复制的本质难题

假设没有 Keeper，两个副本 A、B 直接互相同步：

```
        Client
       ┌─┴─┐
       ▼   ▼
      A     B      ← 两个副本同时接收写入

问题场景（网络分区）：
  某一刻 A 和 B 之间网络断了，但都还活着
  → A 认为"B 挂了，我一个人服务"
  → B 认为"A 挂了，我一个人服务"
  → 两边各自接收写入，各自演化出【不同的数据】
  → 网络恢复后，两边的数据【无法合并】（都改了同一行）

这就是【脑裂】(Split Brain)：两个"大脑"都认为自己是主。
```

**分布式系统的第一性原理：两个节点对"谁是主 / 什么顺序写入"达成一致，本质上需要某种通信。**
而通信本身可能失败（网络分区、消息丢失、机器宕机）——这就是为什么需要一个**专门的协调服务**，并且它必须用**共识算法**（多数派投票）来容错。

## 第 1 章：Quorum（多数派）的数学——共识的根基

### 1.1 为什么是"多数派"而不是"全部"

直觉：写入要所有副本确认才安全？错——任何一个副本宕机就全停，可用性极差。

**Quorum 的魔法：只要"多数派"（过半）同意即可：**

```
3 节点集群，容忍 1 台宕机：
  任何"多数派" = 2 台
  → 任意两个多数派【必然有交集】！

数学证明（鸽笼原理）：
  {A,B} 和 {B,C} —— 交集是 B
  {A,B} 和 {A,C} —— 交集是 A
  {A,C} 和 {B,C} —— 交集是 C
  3 选 2 的任意两组，交集至少 1 个

→ 有交集意味着：新决定一定能"看到"上一批决定中至少一个参与者
→ 不会出现两个不相交的多数派做出两个冲突决定
→ 脑裂被数学上杜绝
```

### 1.2 容错能力表

```
节点数   多数派需要   容忍宕机
  3         2           1     ← 最小生产配置（ClickHouse Keeper 推荐）
  4         3           1     ← 4 台不比 3 台更容错！（浪费）
  5         3           2
  7         4           3

⚠ 这就是为什么 Keeper 部署【奇数台】：4 台的容错能力和 3 台一样，多花钱不多容错。
⚠ 偶数台只有坏处：写入 quorum 要求更高（4 台要 3 票 vs 3 台要 2 票），延迟更高。
```

> **记住：共识 = 多数派投票；多数派必有交集；交集保证不脑裂。3 台起步、永远奇数台。**

## 第 2 章：复制状态机（Replicated State Machine）——一切复制的理论模型

ClickHouse 复制、Raft、ZAB、etcd、Kafka ISR……全部基于同一个理论模型：

```
┌───────────────────────────────────────────────────────┐
│  复制状态机 (RSM) 模型                                  │
│                                                        │
│  核心：复制的不是【数据】，而是【操作日志】              │
│                                                        │
│   客户端命令 ──► ┌─────── 日志（有序）───────┐           │
│                  │ entry1: INSERT part X     │           │
│                  │ entry2: MERGE X+Y→Z      │           │
│                  │ entry3: MUTATION ...      │           │
│                  └──────┬───────────────────┘           │
│                         │ 各副本按【相同顺序】回放日志    │
│            ┌────────────┼────────────┐                  │
│            ▼            ▼            ▼                  │
│        副本A状态      副本B状态      副本C状态            │
│        (相同)         (相同)         (相同)              │
│                                                        │
│  两个保证：                                            │
│  ① 确定性：相同初始状态 + 相同日志顺序 = 相同最终状态     │
│  ② 共识保证：日志顺序在多数派上达成一致（不会两个版本）   │
└───────────────────────────────────────────────────────┘
```

**为什么复制"日志"而不是直接复制"数据"？**
- 日志是有序、增量的 → 天然可回放、可补齐（落后副本只要补日志尾部）
- 操作通常比数据小（一条 "MERGE X+Y→Z" 比几百 GB 的合并结果小得多）
- 确定性回放保证各副本状态收敛一致

**ClickHouse 的对应实现**：
- 日志 = Keeper 上的 `/log` znode 序列
- 回放 = 各副本拉取 entry → 执行（拉 part 或本地重算）
- 状态 = "该副本持有的 part 集合"

## 第 3 章：共识协议底层——ZAB vs Raft（ZK vs Keeper 的差异）

ClickHouse 支持两种协调者：ZooKeeper（ZAB 协议，Java）和 ClickHouse Keeper（Raft 协议，C++）。

### 3.1 共识协议要解决的三个子问题

```
① Leader 选举：谁是主？（网络分区后怎么选出不脑裂的新主？→ 用多数派投票）
② 日志复制：主怎么把日志同步到从？→ 主写日志，多数派确认后"提交"
③ 安全性：  新主必须有全部已提交日志 → 只投票给日志最新的候选者
```

### 3.2 Raft（Keeper 用）的核心流程

```
┌────────────── 任期 (Term) 机制 ──────────────┐
│ 每次选举产生新任期号（递增，类似"朝代更替"）     │
│                                              │
│   ① 选举：节点先给自己投票，随机退避后拉票      │
│      获【多数派】选票 → 成为 Leader           │
│                                              │
│   ② 复制：所有写请求发 Leader                │
│      Leader 追加日志 → 并行发给 Follower      │
│      多数派确认 → 提交(Commit) → 应用状态机   │
│                                              │
│   ③ 脑裂场景：旧 Leader 被隔离               │
│      它无法获得多数派确认 → 写入永不提交       │
│      多数派选出新 Leader → 集群继续服务       │
│      旧 Leader 恢复后发现自己任期旧 → 退位成 Follower│
└──────────────────────────────────────────────┘
```

### 3.3 ZAB（ZooKeeper 用）简述

ZAB（ZooKeeper Atomic Broadcast）思想类似：单一 Leader 广播、多数派确认、epoch 纪元（等价于 term）。实现细节不同（两阶段提交风格、crash recovery 流程更复杂）。

### 3.4 为什么 ClickHouse 自己造了 Keeper

```
ZooKeeper（Java）痛点              ClickHouse Keeper（C++）改进
─────────────────────────────      ─────────────────────────────
JVM：GC 停顿（几秒级）              无 GC，延迟稳定（顺带响应快数倍）
heap 几 GB 装不下百万 znode          内存效率高，同样硬件装更多
需独立部署 JDK 环境                  与 clickhouse-server 同一二进制！
watch 是一次性的，重复注册开销        支持更高效的 watch
snapshot/txn log 管理复杂           更精简的实现

协议层面：Keeper 用 Raft（更易理解/实现正确），ZK 用 ZAB
两者对 CH 暴露的 API 兼容（CH 客户端协议兼容）
→ 可替换，但【同一集群不能混用】（协议细节、事务语义有差异）
```

### 3.5 Watch 机制（CH 复制的"通知系统"）

```
Watch = 客户端在某个 znode 上注册的【一次性】监听器

副本 B 在 /log 上注册 watch
  → 副本 A 写入 entry#4 到 /log
  → Keeper 【立即通知】B："log 变了"
  → B 被动醒来，拉取 entry#4 执行

注意：
① watch 是一次性的（触发后失效，B 要重新注册）→ 避免重复通知
② watch 只说"变了"，不传数据内容 → B 还要自己来读（拉模式）
③ 如果 B 错过通知（重启等），靠【定期对账】兜底（比对 log pointer）
```

> 这解释了 CH 文档那句"每次 INSERT 约在 ZooKeeper 产生 10 个 znode 操作"——日志追加、多个 watch 触发、队列更新等，都是小事务，但**数据本身从不经过 Keeper**（下一章）。

## 第 4 章：ClickHouse 复制架构——什么走 Keeper，什么不走

这是最容易被误解的点，必须彻底澄清：

```
┌─────────────────────────────────────────────────────────────┐
│  ★ Keeper 只存【元数据和操作日志】，从不存数据本体！★          │
│                                                              │
│   走 Keeper 的（小、频繁）：                                  │
│     • 复制日志（INSERT/MERGE/MUTATION 的 entry）              │
│     • 表结构、副本列表、log pointer、任务队列                  │
│     • 数据块的【去重哈希】（幂等 INSERT）                      │
│     • 分布式 DDL 队列（ON CLUSTER 的任务分发）                 │
│                                                              │
│   不走 Keeper 的（大、副本直传）：                             │
│     • part 的实际数据 → 副本之间【点对点 fetch】               │
│       （为什么？数据动辄几百 MB~GB，塞进 Keeper 会被打爆；      │
│         Keeper 的定位是元数据共识，不是数据管道）               │
└─────────────────────────────────────────────────────────────┘

完整的一次 INSERT 复制时序：

Client ──INSERT──► 副本A（任意副本都行，多主架构）
   ①  A 本地内存排序 → 写本地磁盘 part X          （数据落 A）
   ②  A 向 Keeper /log 追加 entry{INSERT, part X 元信息+校验和}
   ③  A 向 Keeper 写入 part X 的 block hash（用于去重幂等）
   ④  A 返回 Client 成功                          ← 不等 B！
   ⑤  Keeper 触发 B 上的 watch
   ⑥  B 拉取 entry → 发现缺 part X
   ⑦  B 直接从 A 【fetch part X】（副本间点对点传输数据）
   ⑧  B 校验（checksums.txt）→ 落盘 → 更新自己的 log pointer

   ⚠ ③④ 之间就返回了 → B 还没拿到数据 → 这就是【最终一致】的来源
   ⚠ 如果 ⑤-⑧ 中 B 宕机 → 恢复后凭 log pointer 发现落后 → 继续补
```

## 第 5 章：log 生命周期的完整闭环

```
┌─────────────────── ① 追加（Append）───────────────────┐
│ 任何副本执行 INSERT/MERGE/MUTATION 都向 /log 追加 entry │
│ entry 内容：操作类型 + part 名称 + 校验和（不含数据！）    │
├─────────────────── ② 感知（Watch）────────────────────┤
│ 其他副本通过 watch 被唤醒，或定期轮询兜底                 │
├─────────────────── ③ 消费（Consume）──────────────────┤
│ 每个副本维护自己的 log_pointer（"我处理到第几条了"）       │
│ 拉取 pointer 之后的新 entry → 放入本地 /queue            │
├─────────────────── ④ 执行（Execute）──────────────────┤
│ 从 queue 逐条执行：                                      │
│   INSERT entry → fetch part（从别的副本拉数据）           │
│   MERGE entry  → 本地重算 或 fetch 合并结果（见第6章）    │
│   MUTATION     → 本地确定性重放                          │
├─────────────────── ⑤ 推进（Advance）──────────────────┤
│ 执行成功 → log_pointer 前移 → 周期性写回 Keeper 持久化    │
├─────────────────── ⑥ 清理（Truncate）──────────────────┤
│ 当【所有副本】都消费到第 N 条 → 日志可截断到 N            │
│ （受 log_rotation_size / log_rotation_period 控制）      │
│ ⚠ 长期离线的副本回来时，日志可能已被清 → 改为全量对账：    │
│   比对自己 part 列表与源分片 → 直接 fetch 缺的 part       │
└─────────────────────────────────────────────────────────┘
```

**副本延迟（replica lag）就是 ⑥ 之前各环节的耗时**：watch 通知延迟 + 网络传输 + B 本地落盘速度。监控 `system.replicas.absolute_delay`。

## 第 6 章：确定性合并——为什么副本可以"抄作业"（最精妙的设计）

### 6.1 合并是确定性的

```
Merge(part X, part Y) 的输入输出完全由算法决定：
  输入：两个已排序的 part（内容不可变）
  操作：k-way 归并排序 + 重建索引/marks
  输出：唯一确定的新 part Z（bit 级可复现！）

相同的输入 + 确定性的算法 = 相同的输出   ← 复制状态机的"确定性"前提
```

### 6.2 协调：合并任务只分配给一个副本

```
没有协调（浪费）：                      有协调（CH 的做法）：
  A: 自己 merge X+Y→Z                    Keeper 给 merge 分配唯一执行者
  B: 自己 merge X+Y→Z  ← 同样的活        entry{MERGE X,Y→Z, assign: A}
  C: 自己 merge X+Y→Z  ← 干三遍！        ┌────────────────────────┐
                                        │ A: 执行 merge，产出 Z    │
                                        │ B: 看到 entry           │
                                        │    → 直接从 A fetch Z ✅ │
                                        │ C: 直接从 A fetch Z ✅   │
                                        └────────────────────────┘
                                        CPU 只花一份，结果三副本共享

细节：
• 执行 merge 的副本因宕机没完成 → Keeper 分配超时 → 改派其他副本
• B 本地已经自己 merge 过了（巧合）→ 校验 part 名相同 → 跳过 fetch
• 这就是 CH 论文/文档里 merges are "assigned" 的含义
```

> **面试金句：ClickHouse 的复制复制的是"操作"，不是"计算结果"由主节点单点算——合并由 Keeper 协调、单副本执行、结果共享。省 CPU 是副本数增加时写入成本不线性增长的根源。**

## 第 7 章：幂等与去重——重复 INSERT 为什么不会重复入库

```
场景：客户端超时重试，同一批数据 INSERT 两次

机制：每次 INSERT 的数据块算出【block_id 哈希】，写入 Keeper
  第 1 次：hash(X) 不存在 → 正常写 part + 记录 hash
  第 2 次：hash(X) 已存在 → 直接返回成功，什么都不做 ✅

边界：
• 去重按【数据块哈希】→ 同一批次的重试有效
• 不同批次的相同数据（业务层重发、分批不同）→ 不会去重！
• 严谨的业务去重要靠：
   ReplacingMergeTree(业务主键+版本) 或 查询层 argMax

分布式表写入的分片去重：
• 写 Distributed 表 → 转发到各分片 → 各分片本地按上述机制去重
```

## 第 8 章：一致性语义与 quorum insert

```
默认（异步复制）：
  写入 → 单副本落盘 + log 追加 → 返回
  一致性：最终一致（秒级收敛）
  可用性：★★★（单副本活着就能写）

insert_quorum = 2（同步等 2 副本）：
  写入 → 等 2 个副本都确认拿到 part → 才返回
  配合 select_sequential_consistency=1：读时保证读到已提交的最新
  一致性：强（读你所写）
  代价：延迟升高、副本故障时写入阻塞
  场景：金融对账等不能容忍读到旧数据的业务

多主（multi-master）含义：
  任何副本都能接收 INSERT/ALTER（没有固定"主库"概念）
  写哪个副本，哪个副本就负责追加 log
  ⚠ 并发写不同副本完全合法，靠 Keeper 日志串行化
```

**为什么 CH 默认选最终一致？** OLAP 负载（报表、分析）通常容忍秒级延迟，而强一致的代价（延迟+可用性）对分析场景不划算——又是一句"负载决定架构"。

## 第 9 章：故障场景推演（面试压力测试最爱）

**场景 1：某副本宕机 1 小时，恢复后怎么追上？**
> ① 看自己的 log_pointer，拉取落后的 entry；② 日志还在 → 逐条补（fetch part）；③ 日志已被截断 → 全量对账（比对 part 列表，直接 fetch 缺失 part）。不需要重放全部历史。

**场景 2：Keeper 集群挂了，会发生什么？**
> **已有查询不受影响**（读本地 part 即可），但**写入、合并、副本同步全部阻塞**（无法追加 log/分配 merge）。CH 进程不挂，只是"不能再变更"。这就是为什么 Keeper 要 3 台以上、跨机房部署。

**场景 3：两个客户端同时 INSERT 到两个不同副本，冲突吗？**
> 不冲突。两个 INSERT 变成两条 log entry，Keeper 串行化（全局有序），两个副本按相同顺序回放 → 状态收敛一致。这就是复制状态机的意义。

**场景 4：副本间版本不一致（A 有 part X，B 没有），查询会怎样？**
> 查询打到不同副本可能返回不同结果（最终一致的体现）。规避：①负载均衡避开延迟副本（`load_balancing`）；②关键读用 quorum insert + sequential consistency；③监控 `absolute_delay` 告警。

**场景 5：误执行 `ALTER TABLE ... DELETE`，所有副本都会执行吗？**
> 会！mutation 也是 log entry，所有副本确定性回放 → **复制不能防误操作**（这就是"复制≠备份"的底层原因）。

## 第 10 章：追问满分回答

**追问 1：为什么数据不直接经过 Keeper 同步？**
> Keeper 定位是元数据共识服务（znode 小、事务轻、要低延迟）。part 动辄几百 MB~GB，塞进 Keeper 会拖垮共识延迟、撑爆其内存。所以 CH 只把"操作日志"放 Keeper，数据由副本间点对点 fetch。

**追问 2：log 会不会无限增长？**
> 会截断：所有副本都消费过的 entry 可清理（`log_rotation_size`/`log_rotation_period`）。长期离线副本恢复时日志可能已删，此时走"全量对账 + fetch part"而非重放。

**追问 3：为什么 Keeper 推荐 3 台而不是 2 台？**
> 2 台的多数派是 2（全部），任一台宕机就不可用，容错 0。3 台多数派是 2，容错 1 台。奇数台是 quorum 数学下的最优性价比（4 台容错仍是 1，白花钱）。

**追问 4：副本越多是不是写入越安全、越快？**
> 安全性提升（容更多副本故障），但**写入吞吐不升反可能降**：每个新副本都要 fetch 一份 part（网络/IO 放大），且更多 watch/queue 压力打到 Keeper。副本数通常 2（够用）最多 3。

**追问 5：新增一个空副本，数据怎么来？**
> 不是从 log 第 0 条重放，而是全量对账：比对源分片的 part 列表 → 逐个 fetch part（大表会自动分批）。期间新副本算"落后"状态，`system.replicas` 可观测进度。

**追问 6：ClickHouse Keeper 和 ZooKeeper 混布在一个集群行不行？**
> 不行。协议层面兼容可整体替换，但混用时两者的事务/watch 细节不一致，会出现难排查的诡异行为。迁移应整体切换。
